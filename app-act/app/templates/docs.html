Überblick

ACT (AI-driven Change Tracking) ist ein internes Ticketsystem, das Bugmeldungen und Feature-Requests über einen eingebetteten Browser-Widget entgegennimmt und den gesamten Lifecycle — von der Erfassung über KI-gestützte Analyse bis zur automatisierten Implementierung — in einem geschlossenen Regelkreis abbildet.

Das System besteht aus drei Schichten: einer FastAPI-Backend-API, einem Jinja2-Web-Frontend und einem einbettbaren Web Component Widget. Eine Python-Brücke (act-claude.py) verbindet das System mit Claude Code CLI für die KI-Operationen.

Ticket-Workflow

Jedes Ticket durchläuft einen definierten Statusgraph. Statusübergänge werden protokolliert und sind vollständig auditierbar.

stateDiagram-v2 [*] --> new : Widget-Einreichung new --> proposed : KI-Analyse erstellt Proposal new --> rejected : Spam / nicht umsetzbar proposed --> approved : Admin genehmigt proposed --> rejected : Admin lehnt ab approved --> implementing : KI startet Implementierung implementing --> testing : Commit + Branch erstellt implementing --> new : Fehler bei Implementierung testing --> done : Admin nimmt ab → Merge + Branch gelöscht testing --> new : Admin lehnt ab → Branch gelöscht, neu planen

Statusbeschreibungen

  • new — Eingegangen, wartet auf KI-Analyse.
  • proposed — KI hat einen Lösungsvorschlag (Proposal) erstellt. Enthält Summary, Dateipfade und Diff-Preview.
  • approved — Admin hat das Proposal freigegeben. Wartet auf Implementierung.
  • implementing — KI arbeitet auf einem Feature-Branch (act/tkt-<id>).
  • testing — Implementierung committed. Branch wartet auf Merge.
  • done — Gemergt, Changelog-Eintrag erstellt.
  • rejected — Manuell oder automatisch abgelehnt (Spam, leerer Diff, verdächtige Commit-Message).

Benutzerhandbuch

Ticket einreichen (Widget)

Das Widget ist auf der Ziel-Applikation eingebettet. Ein Klick auf den "Feedback"-Button öffnet ein Formular. Typ (Bug / Feature), Titel und Beschreibung sind Pflichtfelder. Browser-Kontext (URL, User-Agent) wird automatisch erfasst.

Dashboard

Das Dashboard unter / zeigt alle offenen Tickets mit Status-Badges, Priorität und Typ. Die Zahl im Nav-Badge entspricht der Anzahl der Tickets im Status new, proposed und approved. Über die Filter- und Suchfunktion lassen sich Tickets nach Status, App und Freitext eingrenzen.

Proposals prüfen und genehmigen

In der Ticket-Detailansicht erscheinen KI-generierte Proposals mit Summary, vorgesehenen Dateipfaden und Diff-Preview. Über die Schaltflächen Approve / Reject wird ein Proposal freigegeben oder abgelehnt. Nur genehmigte Proposals werden implementiert.

Backlog

Der Backlog unter /backlog dient als Ideenspeicher. Einträge können manuell erstellt und bei Bedarf als reguläres Ticket promoted werden.

Changelog

Unter /changelog wird jede abgeschlossene Änderung pro App mit Commit-Hash und geänderten Dateien angezeigt.

KI-Brücke (act-claude.py)

act-claude.py ist der Automatisierungs-Layer zwischen ACT und Claude Code CLI. Es läuft als Cronjob auf dem Host und spricht über die REST-API mit dem ACT-Backend.

flowchart LR A[Cronjob] --> B[act-claude.py] B -->|GET /api/tickets| C[ACT API] B -->|claude --print| D[Claude Code CLI] D --> B B -->|POST /api/tickets/tkt/transition| C B -->|git checkout -b / commit| E[Git Repo] C --> F[(SQLite DB)]

Kommandos

  • ./act-claude.py analyze — Analysiert alle Tickets im Status new, erstellt Proposals.
  • ./act-claude.py implement [TKT-ID] — Implementiert ein approved Ticket auf einem Branch.
  • ./act-claude.py auto — Kombiniert analyze + implement (Vollzyklus).
  • ./act-claude.py status — Zeigt alle Tickets mit handlungsbedarf.

Sicherheits-Checks

Vor dem Merge werden implementierte Branches auf leere Diffs und verdächtige Commit-Messages geprüft. Schlägt ein Check fehl, wird der Branch verworfen und das Ticket zurückgesetzt.

Bei einem Absturz während der Implementierung bleibt das Ticket im Status implementing hängen. Manuelles Zurücksetzen über die API oder direkt in der DB ist dann erforderlich.

Widget (act-widget.js)

Das Widget ist ein Vanilla-JS Web Component (Shadow DOM), das in jede Anwendung eingebettet werden kann. Es benötigt einen App-Token und den ACT-Endpoint. 

<act-widget
  endpoint="https://act.claude.int"
  token="act_<app-token>"
  mode="link"
  label="Feedback"
></act-widget>
<script src="https://act.claude.int/widget/act-widget.js"></script>

Parameter: mode="link" zeigt einen Link, mode="button" einen Button. label setzt den sichtbaren Text.

DORA

Der Digital Operationally Resilience Act (DORA, EU 2022/2554) ist eine EU-Verordnung, die verbindliche Anforderungen an die digitale Betriebsstabilität von Finanzunternehmen stellt. Sie verpflichtet Banken, Versicherungen, Wertpapierfirmen und weitere Finanzmarktteilnehmer zu einem robusten IKT-Risikomanagement, lückenlosen Auditierbarkeit von IKT-Systemen und -Prozessen, strukturiertem Incident-Reporting gegenüber Aufsichtsbehörden sowie zur Stärkung der Cyber-Resilienz gegenüber Angriffen und Betriebsunterbrechungen.

Quelle: Verordnung (EU) 2022/2554 des Europäischen Parlaments und des Rates vom 14. Dezember 2022 über die digitale operationale Resilienz im Finanzsektor (DORA). Anwendbar ab 17. Januar 2025.

IKT-Risikomanagement
Finanzunternehmen müssen ein umfassendes IKT-Risikomanagement implementieren, dokumentieren und regelmäßig prüfen (Art. 5–15 DORA).
Incident-Meldepflicht
Schwerwiegende IKT-bezogene Vorfälle müssen klassifiziert und fristgerecht an die zuständige Aufsichtsbehörde gemeldet werden (Art. 17–23 DORA).
Resilienz-Tests
Regelmäßige Tests der IKT-Systeme sind verpflichtend — von einfachen Schwachstellenscans bis zu bedrohungsgeleiteten Penetrationstests (TLPT, Art. 24–27 DORA).
Drittparteienrisiko
Vertragsbeziehungen mit IKT-Drittdienstleistern müssen dokumentiert, bewertet und ausfallsicher ausgestaltet sein (Art. 28–44 DORA).

Bezug zu ACT

ACT adressiert mehrere DORA-relevante Anforderungen: Der vollständige Changelog mit Commit-Hashes und geänderten Dateien liefert den Audit-Trail, den Art. 9 DORA für die Nachvollziehbarkeit von IKT-Änderungen fordert. Der strukturierte Proposal-Review-Prozess (Analyse → Genehmigung → Implementierung) entspricht dem Change-Control-Gedanken des IKT-Risikomanagements. Bug-Tickets dokumentieren Incidents mit Kontext und ermöglichen über git revert eine nachvollziehbare Wiederherstellung.

DORA gilt unmittelbar für Finanzunternehmen und deren IKT-Drittdienstleister im Sinne der Verordnung. ACT ist kein reguliertes Finanzprodukt — die beschriebenen Parallelen sind konzeptioneller Natur und relevant, sofern ACT im Umfeld eines DORA-pflichtigen Unternehmens eingesetzt wird.

ITIL Referenz

ITIL 4 (Information Technology Infrastructure Library) ist ein Framework für IT-Service-Management. Die aktuelle Version ITIL 4 wurde 2019 von Axelos veröffentlicht und stellt den Service Value System (SVS) in den Mittelpunkt.

Quelle: Axelos — ITIL Foundation: ITIL 4 Edition, TSO, 2019, ISBN 978-0-11-331607-3. Axelos ist die offizielle Herausgeberorganisation für ITIL.

Relevante ITIL-4-Practices

Change Enablement
Maximiert Erfolgsrate von IT-Änderungen durch Risikobewertung und Genehmigungsprozesse. ACT bildet dies durch den Proposal-Review-Schritt ab.
Incident Management
Minimiert negative Auswirkungen durch schnelle Wiederherstellung. Bug-Tickets in ACT entsprechen Incident-Records; Rollback via git revert ist der Restore-Mechanismus.
Problem Management
Identifiziert Ursachen wiederkehrender Incidents. Der Backlog in ACT kann als Problem-Register genutzt werden.
Service Request Management
Bearbeitet standardisierte Anfragen. Feature-Tickets in ACT entsprechen Service Requests.
Continual Improvement
Systematische Verbesserung von Services. Der Changelog in ACT liefert den Audit-Trail für Improvement-Aktivitäten.
ACT ist kein zertifiziertes ITIL-Werkzeug. Die Parallelen sind konzeptioneller Natur. Für eine vollständige ITIL-4-Konformität wären zusätzliche Prozesse und Dokumentation erforderlich (z. B. Configuration Management Database, Service Level Agreements, Supplier Management).

Technischer Stack

  • Backend: Python 3.12, FastAPI, SQLite (WAL-Modus für Concurrent Reads)
  • Frontend: Jinja2 Templates, Vanilla JS — kein Build-Step erforderlich
  • Widget: Vanilla JS Web Component (Shadow DOM), einbettbar in beliebige Anwendungen
  • Container: Docker, hinter Traefik Reverse Proxy mit TLS-Terminierung
  • Notifications: ntfy (Self-hosted Push-Notification-Server, JSON API)
  • KI: Claude Code CLI via claude --print (kein API-Key erforderlich, nutzt lokale Authentifizierung)
